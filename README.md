# Trace Mining: Understanding AI Agent Usage & Token Consumption

## Overview

This project analyzes **50,000 LLM call records** generated by AI agents across different business domains, including customer service, coding, shopping, and personal assistance.

The objective is to answer two fundamental business questions:

- **What are AI agents actually being used for?**
- **Where are the tokens being consumed, and how can usage be optimized?**

The raw logs contain individual LLM calls, but understanding agent behavior requires analyzing complete sessions rather than isolated requests. This project transforms raw traces into a structured business taxonomy, performs accurate token accounting, and generates actionable insights into AI agent usage and cost optimization.

---

## 1. Problem Statement

The goal is to organize agent activity into a three-level hierarchy:

```text
Business Use Case
    └── Workflow
          └── Trace
                └── LLM Calls
```

### Example

```text
Airline Customer Service
    └── Flight Change
          └── Trace: 4a73...
                ├── Call 1: Understand user request
                ├── Call 2: Retrieve booking details
                ├── Call 3: Check flight availability
                └── Call 4: Confirm flight change
```

### Key Deliverables

- **Hierarchical Taxonomy:** Business use cases and workflows identified from agent traces.
- **Trace Classification:** Every trace assigned to an appropriate workflow.
- **Token Accounting:** Calls, input tokens, output tokens, and token shares aggregated at every hierarchy level.
- **Representative Examples:** Short excerpts illustrating the behavior of each workflow.
- **Reliable Data Handling:** Recorded, estimated, and unknown token values maintained separately.
- **Human-Readable Visualization:** HTML viewer for exploring the analysis.
- **Machine-Readable Output:** Structured JSON containing classifications and aggregated statistics.

---

## 2. Key Concepts

| Concept | Description |
|---|---|
| Call / Span | A single LLM request and response, represented by one log record. |
| Trace / Session | A collection of LLM calls belonging to one agent task, identified by `trace_id`. |
| Use Case | A high-level business function, such as Telecom Customer Support. |
| Workflow | A specific task within a use case, such as Enabling Roaming. |
| Trace Classification | Assigning an entire session to a business use case and workflow. |

### Why Classify Traces Instead of Calls?

Individual calls often lack sufficient context to identify their purpose.

For example, a tool call named `get_user_details` could appear in customer support, shopping, or personal assistant workflows.

Analyzing the complete trace reveals the actual intent and sequence of actions.

This reduces the classification problem from **50,000 individual calls to 3,154 traces**, making the analysis more efficient and meaningful.

## 3. Methodology

The solution follows a structured pipeline combining exploratory data analysis, deterministic signals, LLM-based semantic classification, and rigorous validation.

### Step 1: Exploratory Data Analysis

Before using LLMs, the dataset was examined to understand its structure and identify useful signals.

Key observations:

- Approximately 50,000 LLM call records.
- 3,154 unique traces.
- 117 distinct tool sets across traces.
- Tool definitions provide strong signals about agent capabilities and business domains.

For example, an agent equipped with `book_reservation` and `cancel_reservation` tools is likely associated with travel or airline services.

**Key insight:** Use inexpensive, deterministic signals before applying expensive LLM-based analysis.

### Step 2: Taxonomy Discovery

An LLM (GLM) was used to propose a meaningful taxonomy of business use cases and workflows.

The process:

1. Group traces using tool-set similarities.
2. Sample representative traces from each cluster.
3. Ask the LLM to identify common business purposes.
4. Construct a predefined taxonomy of use cases and workflows.
5. Refine labels to ensure consistency and avoid unnecessary fragmentation.

This creates a fixed classification vocabulary instead of allowing hundreds of inconsistent labels.

### Step 3: Trace Digest Construction

Long traces containing dozens or even hundreds of calls cannot be efficiently passed directly to an LLM.

Each trace was therefore compressed into a concise digest containing:

- Available tools and their descriptions.
- Tools actually invoked during execution.
- The user's original request.
- Relevant observations and intermediate actions.
- Context needed to identify the business objective.

#### Extracting the Actual User Intent

One major challenge was locating the user's actual request within lengthy agent prompts.

For example:

```text
First Observation:
message = "My flight was delayed..."
```

Extracting this information significantly improved classification quality and reduced the number of traces assigned to `Other / Unclear`.

**Key insight:** The quality of the trace representation directly determines the quality of classification.

### Step 4: LLM-Based Trace Classification

Once the taxonomy was established, traces were classified into the predefined use cases and workflows.

The classification process incorporated:

- Fixed taxonomy labels.
- Batched LLM requests.
- Parallel execution.
- Cached responses.
- Structured outputs.
- Fallback assignments based on tool-set majority labels.

This approach improved consistency, reduced API overhead, and ensured that every trace received a classification.

### Step 5: Token Accounting and Aggregation

Token usage was aggregated at the trace, workflow, and business use-case levels.

#### Important Accounting Rules

| Rule | Treatment |
|---|---|
| Missing token values | Remain unknown; never silently convert to zero. |
| Recorded token counts | Report separately from estimated counts. |
| Estimated token counts | Maintain separate estimates and methodology. |
| Session-level usage | Do not add again when already represented by per-call totals. |
| Cache tokens | Avoid double-counting when already included in input tokens. |
| Token shares | Explicitly define the denominator. |

The token share in this analysis uses **recorded input + output tokens** as the denominator.

All aggregation logic was designed to preserve accounting consistency.

### Step 6: Validation and Error Correction

Automated classification can produce systematic errors, especially when tool names are misleading.

One identified issue involved **242 personal-assistant traces incorrectly classified as shopping workflows**, because the model relied heavily on `amazon__*` tool names.

This was corrected using additional contextual evidence.

Validation included:

- Checking that every trace had an assignment.
- Comparing aggregate counts across hierarchy levels.
- Verifying token totals against the original dataset.
- Checking that workflow totals reconcile with use-case totals.
- Ensuring the total call count remains 50,000.
- Ensuring recorded token totals reconcile to approximately 1.6 billion.

### Step 7: Output Generation

The final analysis produces two complementary outputs:

**JSON**
- Trace assignments.
- Use-case and workflow hierarchy.
- Aggregated statistics.
- Token accounting.
- Representative examples.

**HTML Viewer**
- Interactive exploration of the taxonomy.
- Workflow-level summaries.
- Token consumption breakdown.
- Representative trace examples.
- Business insights and findings.

## 4. Key Findings

The analysis revealed several important patterns in AI agent usage and token consumption.

### Finding 1: Input Tokens Dominate Consumption

Input token consumption is approximately **133× output token consumption**.

This indicates that agents repeatedly send large amounts of contextual information during execution.

**Implication:** Prompt caching, context compression, and reducing redundant context are potentially high-impact optimization strategies.

### Finding 2: Token Consumption Is Highly Concentrated

The top 10% of traces account for approximately **66% of total token consumption**.

This indicates a highly skewed distribution in which a relatively small number of sessions consume a disproportionate amount of resources.

**Implication:** Prioritize long-session optimization, context summarization, and token budgets for high-consumption workflows.

### Finding 3: Tool Sets Reveal Agent Capabilities

The 117 distinct tool sets provide meaningful structural information about agent behavior.

**Implication:** Tool-based clustering can substantially reduce classification complexity before applying semantic analysis.

### Finding 4: Context Extraction Improves Classification

Extracting the original user request from lengthy traces substantially improves semantic classification.

**Implication:** Better preprocessing can be more effective than simply increasing the complexity of the classification model.
